# แผนพัฒนา LINE Group Mapping สำหรับกลุ่มงาน/ห้องเวร

สถานะ: implemented ในโค้ด — ต้องรัน migration และตั้งค่าใน Supabase/LINE ก่อนใช้งานจริง

เอกสารนี้เป็นแผนต่อยอดจาก LINE Integration เดิม เพื่อให้แต่ละกลุ่มงาน/ห้องเวรเลือกกลุ่ม LINE ที่ใช้รับประกาศได้อย่างถูกต้อง โดยยังใช้ LINE OA เดียวและใช้ระบบเว็บเป็น Single Source of Truth

## 1. เป้าหมาย

- ให้ Admin ผูกกลุ่มงาน/ห้องเวรในระบบกับ LINE Group ID ได้จากหน้า Admin → ตั้งค่าระบบ
- เมื่อสร้างกลุ่มงาน/ห้องเวรใหม่ ให้แสดงรายการใหม่ในหน้าตั้งค่าโดยอัตโนมัติ
- ส่งประกาศขายเวรแบบรับคนแรกไปเฉพาะกลุ่ม LINE ที่ผูกกับกลุ่มงานของเวรนั้น
- รองรับการส่งสรุปเวรรายวันแยกตามกลุ่มงานด้วย mapping เดียวกัน
- เก็บสถานะ อนุมัติ/เปิดใช้งาน/ยกเลิก mapping และ audit การเปลี่ยนแปลง
- ไม่กระทบ notification ส่วนตัวของการแลกเวรและการขายเวรแบบระบุผู้ซื้อ

## 2. ขอบเขตที่ไม่รวมในรอบแรก

- ไม่สร้าง LINE OA แยกต่อกลุ่มงาน
- ไม่ให้ LINE Group แก้ไขตารางเวรโดยตรง
- ไม่ประกาศคำขอแลกเวรหรือขายเวรแบบระบุผู้ซื้อเข้า group โดยอัตโนมัติ
- ไม่ผูก mapping จากชื่อกลุ่ม LINE ที่ผู้ใช้กรอกเองโดยไม่มีการตรวจสอบ

## 3. โครงสร้างข้อมูลปัจจุบันและช่องว่าง

ระบบมีโครงสร้างแยกกันอยู่แล้ว:

- `shift_teams` = กลุ่มงาน/ห้อง/หน่วยงานของตารางเวร
- `shift_shift_types` = ประเภทเวร เช่น เช้า บ่าย ดึก หรือแบบอื่น
- `shift_line_groups` = LINE group ที่ OA ตรวจพบ พร้อมสถานะ active/approved และการรับ daily roster

ปัจจุบัน `shift_line_groups` ยังไม่มีความสัมพันธ์กับ `shift_teams` หรือ `shift_shift_types` ดังนั้นประกาศกลุ่มจะถูกส่งแบบรวมไปยังทุกกลุ่มที่อนุมัติอยู่

## 4. แบบจำลอง mapping ที่เสนอ

แนะนำให้สร้างตารางแยก `shift_line_group_mappings` แทนการใส่คอลัมน์เดียวใน `shift_teams` เพื่อรองรับการขยายในอนาคต

ฟิลด์หลัก:

- `id`
- `team_id` → กลุ่มงาน/ห้องใน `shift_teams`
- `line_group_id` → แถวกลุ่มใน `shift_line_groups` (เก็บ LINE Group ID จริงไว้ที่ตารางเดิม)
- `shift_type_id` nullable → ถ้าต้องการแยกเฉพาะประเภทเวร
- `is_active`
- `created_by`, `created_at`, `updated_at`

ความหมายของ mapping:

- `team_id` อย่างเดียว = ทุกประเภทเวรในกลุ่มงานนั้น
- `team_id + shift_type_id` = เฉพาะประเภทเวรนั้น
- mapping เฉพาะประเภทเวรควรมี priority เหนือ mapping ระดับกลุ่มงาน
- โครงสร้างรองรับหนึ่งกลุ่มงานมีหลายกลุ่ม LINE ได้ แม้ค่าเริ่มต้นจะแนะนำหนึ่งกลุ่มงานต่อหนึ่งกลุ่ม LINE

กติกาเริ่มต้นที่แนะนำ:

- หนึ่งกลุ่มงาน/ห้อง → หนึ่ง LINE Group
- หากไม่มี mapping → ไม่ส่งประกาศเข้ากลุ่ม เพื่อป้องกันข้อมูลรั่วไปผิดกลุ่ม
- notification ส่วนตัวยังส่งตามผู้ใช้ที่เกี่ยวข้องเหมือนเดิม

## 5. หน้าตั้งค่าสำหรับ Admin

เพิ่มส่วน `LINE Group Mapping` ในหน้า Admin → ตั้งค่าระบบ โดยแสดงรายการจาก `shift_teams` แบบ dynamic

แต่ละแถวควรแสดง:

- ชื่อและรหัสกลุ่มงาน/ห้อง
- ประเภทเวรที่ผูก (ถ้ามี)
- ช่องกรอก `LINE Group ID`
- ชื่อกลุ่ม LINE และสถานะที่ OA ตรวจพบ
- สถานะ approved/active
- ปุ่มบันทึก แก้ไข ล้าง mapping และทดสอบส่งข้อความ
- วันเวลาแก้ไขล่าสุดและผู้แก้ไข

เมื่อเพิ่มกลุ่มงานใหม่ในระบบ รายการจะปรากฏในหน้านี้จากการอ่าน `shift_teams` โดยไม่ต้องเพิ่มเมนูหรือโค้ดเฉพาะกลุ่มงานใหม่

แนวทาง UX ที่แนะนำ:

1. OA ถูกเชิญเข้ากลุ่ม LINE
2. webhook บันทึก group ID เป็นกลุ่มใหม่ที่ยังไม่อนุมัติ
3. Admin เลือกกลุ่มที่ตรวจพบ หรือกรอก Group ID เอง
4. Admin ผูกกับกลุ่มงาน/ประเภทเวร แล้วกดบันทึก
5. Admin อนุมัติและเปิดใช้งานกลุ่ม

หากกรอก ID ที่ OA ยังไม่เคยพบ ควรแสดงสถานะ `รอตรวจพบ/รออนุมัติ` และยังไม่ส่งข้อมูลจนกว่าจะตรวจสอบสำเร็จ

## 6. การเลือกผู้รับประกาศ

สร้าง service กลางสำหรับ resolve กลุ่มผู้รับ เช่น `resolveLineGroupsForAssignments()` โดยใช้ assignment เป็น source of truth

### ประกาศขายเวรแบบรับคนแรก

- อ่าน `team_id` และ `shift_type_id` จาก assignment ของรายการขาย
- เลือก mapping ที่ active และกลุ่ม LINE ที่ active + approved
- ใช้ mapping เฉพาะประเภทเวรก่อน แล้ว fallback ไป mapping ระดับกลุ่มงาน
- ส่งเฉพาะกลุ่มที่ตรงกับเวรนั้น
- dedupe key ต้องรวม sale ID และ LINE group ID

### สรุปเวรรายวัน

- สร้าง roster แยกตาม mapping ของแต่ละกลุ่ม
- กลุ่มห้องปฏิบัติการกลางเห็นเฉพาะข้อมูลของห้องปฏิบัติการกลาง
- กลุ่มผู้ช่วยเห็นเฉพาะข้อมูลของกลุ่มผู้ช่วย
- การเปิดเผยเบอร์โทรยังต้องผ่าน setting ระดับระบบและระดับกลุ่มเหมือนเดิม

### การแจ้งเตือนส่วนตัว

- แลกเวร: ส่งให้ผู้ขอ ผู้รับคำขอ และผู้อนุมัติที่เกี่ยวข้อง
- ขายเวรแบบระบุผู้ซื้อ: ส่งให้ผู้ขาย ผู้ซื้อ และผู้อนุมัติที่เกี่ยวข้อง
- การ mapping กลุ่มไม่เปลี่ยนเส้นทาง notification ส่วนตัว

## 7. จุดที่ต้องปรับในโค้ด

- Migration ใหม่สำหรับ `shift_line_group_mappings`, foreign keys, unique/index และ service-role-only RLS
- Admin API ใหม่ `/api/admin/line/mappings` สำหรับอ่าน teams/shift types/mappings และ `/api/admin/line/mappings/[id]` สำหรับแก้ไข/ล้าง
- API สำหรับ create/update/delete mapping พร้อมตรวจสิทธิ์ Admin และเขียน audit
- `components/admin/line-group-mapping-card.tsx` เพิ่มตารางและฟอร์ม mappingในหน้า `Admin → ตั้งค่าระบบ`
- `lib/server/line-notify.ts` เพิ่ม resolver สำหรับส่งตาม mapping แทนการ broadcast แบบ global
- `lib/server/line-scheduled.ts` สร้าง daily roster ตามกลุ่มงาน/ประเภทเวร
- `lib/server/line-data.ts` รองรับ filter `team_id` และ `shift_type_id`
- `lib/server/line-mutations.ts` เรียก resolver ตอนสร้างประกาศขายเวร
- webhook join/leave ให้รักษาสถานะ mapping เมื่อกลุ่มถูกเพิ่มหรือนำ OA ออก

## 8. ความปลอดภัยและความถูกต้อง

- เขียน mapping ได้เฉพาะ Admin
- ตรวจว่า `team_id`, `shift_type_id` และกลุ่ม LINE มีอยู่จริง
- กลุ่มที่ไม่ approved หรือ inactive ห้ามรับข้อมูล
- ไม่เชื่อชื่อกลุ่มจาก client เป็นตัวตัดสินสิทธิ์
- ไม่ส่งข้อมูลของทีมอื่นข้าม mapping
- ทุกการสร้าง แก้ไข ล้าง และเปิด/ปิด mapping ต้องมี audit log
- หาก LINE ส่งไม่สำเร็จ ให้ retry ผ่าน outbox โดยไม่ rollback การเปลี่ยนแปลงตารางเวร

## 9. แผน migration และ rollout

1. เพิ่ม schema และ RLS โดยไม่เปลี่ยนพฤติกรรมเดิม
2. เพิ่ม read-only mapping list ใน Admin
3. เพิ่มการบันทึก/แก้ไข mapping และ audit
4. เพิ่ม resolver และทดสอบการเลือกกลุ่ม
5. เปลี่ยนประกาศขายเวรและ daily roster ให้ใช้ mapping
6. ทดสอบกลุ่มที่ไม่มี mapping, กลุ่มถูกปิด, OA ออกจากกลุ่ม และ mapping ซ้ำ
7. ให้ Admin ตั้งค่า mapping จริงใน staging
8. เปิด feature flag สำหรับ production หลัง UAT

กลุ่ม LINE เดิมที่ยังไม่มี mapping จะไม่ถูกผูกให้อัตโนมัติ ต้องให้ Admin ตรวจสอบและเลือกเอง

## 10. Acceptance criteria

- สร้างกลุ่มงานใหม่แล้วเห็นรายการใหม่ในหน้า Admin โดยอัตโนมัติ
- Admin ที่ไม่ใช่ผู้มีสิทธิ์แก้ mapping ไม่สามารถบันทึกได้
- ผูกห้องปฏิบัติการกลางกับ Group A แล้ว ประกาศขายเวรของห้องนี้เข้าเฉพาะ Group A
- ผูกเวรผู้ช่วยกับ Group B แล้ว ประกาศขายเวรของผู้ช่วยเข้าเฉพาะ Group B
- กลุ่มที่ไม่ผูกหรือไม่ approved ไม่ได้รับประกาศ
- daily roster ของแต่ละกลุ่มไม่แสดงข้อมูลของกลุ่มงานอื่น
- การแลกเวรและขายเวรแบบระบุผู้ซื้อยังส่ง notification ส่วนตัวได้ตามเดิม
- การเพิ่ม/แก้ไข/ล้าง mapping มี audit log
- ใช้ LINE OA เดียวส่งได้หลาย group
- ผ่าน typecheck, lint, unit/integration tests และ UAT บน staging

## 11. ประเด็นที่ต้องยืนยันก่อนเริ่ม implementation

ค่าเริ่มต้นที่แนะนำคือ:

1. หนึ่งกลุ่มงานผูกได้หนึ่ง LINE Group แต่ schema รองรับหลายกลุ่ม
2. ใช้ mapping ระดับกลุ่มงานก่อน และเปิด mapping ตามประเภทเวรเป็นตัวเลือก
3. ใช้ mapping เดียวกันทั้งประกาศขายเวรและ daily roster
4. กลุ่มที่ไม่มี mapping จะไม่รับประกาศ
5. Admin เลือกจากกลุ่มที่ OA ตรวจพบ หรือกรอก Group ID เองได้ แต่ต้องรอการตรวจสอบ/อนุมัติ

ส่วน implementation ใน repository ครอบคลุม migration, Admin API, Admin UI และ routing แล้ว เหลือการรัน migration, ตั้งค่า LINE Console และ UAT ก่อนเปิดใช้งานจริง
